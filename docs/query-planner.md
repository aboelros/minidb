# Query Planner Subsystem

The Query Planner sits between the SQL Parser and the Executor. It takes the Abstract Syntax Tree (AST) generated by the parser and translates it into an optimized execution plan.

## 1. Logical Plan
The `LogicalPlan` represents *what* the query wants to do, without specifying *how* to do it.

Example SQL:
```sql
SELECT name, age FROM users WHERE age > 18 LIMIT 10;
```

Logical Plan Tree:
```text
Projection (name, age)
  └── Limit (10)
       └── Filter (age > 18)
            └── SeqScan (users)
```

## 2. Physical Plan
The `PhysicalPlan` takes the Logical Plan and makes concrete decisions on *how* to execute it based on the database's physical structures (like indexes).

For the previous example, if there is an index on `age`, the physical plan might become:
```text
Projection (name, age)
  └── Limit (10)
       └── IndexScan (idx_age, age > 18)
```
Notice how `Filter` and `SeqScan` were collapsed into an `IndexScan`. If no index exists, the physical plan looks nearly identical to the logical plan.

## 3. The Planner
The `Planner` struct is responsible for two main functions:
1. `create_logical_plan(Statement) -> LogicalPlan`: Translates an AST statement into a Logical Plan tree.
2. `create_physical_plan(LogicalPlan) -> PhysicalPlan`: Optimizes the Logical Plan (by consulting the catalog for indexes) and produces the Physical Plan.

The resulting Physical Plan is then traversed to instantiate the actual `Executor` pipeline for query evaluation.
